# Multi-ROM region travel (Cormoria first)

## User contract

Entering Cormoria automatically switches to the Cormoria ROM. Leaving switches back to the existing-world ROM. Keep the player's identity, Pokémon (party and PC), items, common menus/settings, and co-op identity intact on every trip in both directions. Keep each world's quests, maps, puzzles, trainers and return position independently. Legacy saves do not need to migrate into this release; the two-ROM flow may start with a new V2 save. Keep the whole Cormoria campaign in its own ROM; do not put both worlds into one binary or require bank-switching hardware.

This replaces the single-binary strategy in [the combined-ROM plan](2026-09-22-1124-feat-cormoria-region-plan.md). Its pinned source inventory and shared-engine compatibility findings remain useful. Work remains in the existing `codex/dreamstone-region` worktree. No deployment, merge or publication is authorized by this plan.

## Implementation decisions

- The user chose to combine the best parts of both games. Build both ROMs from a shared Hoenn Sessions engine: retain its co-op, Pokémon roster and progression; adapt Dreamstone's expanded bag, quest journal and regional adventure. Menus, item definitions, Pokémon definitions and save structures must agree across both builds. World content is selected at build time.
- Keep Dreamstone's campaign source pinned at `f7997186345885bfa23a170e5f573851fc034b9b`, with explicit import transformations and reproducible build inputs. Preserve its campaign and source attribution. The original donor build is a behavioral reference, not a compatible drop-in second ROM.
- Treat each ROM and its matching save/bridge descriptor as a separate verified artifact. A shared release identity must not pretend that the ROM hashes or memory addresses are identical.
- Model ROM travel through a world catalog with stable world IDs, artifact identity, save namespace, portal arrival and return positions, and bridge descriptor per world. The checkpoint, transfer, shutdown, launch and recovery code must take source and destination IDs rather than special-case Cormoria. Register Cormoria first; later regions add catalog/content entries and a schema version when their regional progress needs new fields.
- Keep one active V2 player authority and one regional save per ROM. Every switch copies and verifies the current shared player state before the destination becomes active; neither direction may drop Pokémon, inventory, settings or co-op identity. Switching is a checkpointed transaction, not copying one game's entire save over the other.
- Start two-ROM travel from a new V2 save in a distinct save namespace. Existing V1 saves are outside the travel contract; no legacy-save migration is required. Reject a V1 file presented as a traveling V2 character.
- Introduce schema version two before enabling travel: `CoopSaveV1` has exactly four regional-progress records and requires bytes 604–667 to be zero. Put Cormoria's eight-byte regional record at 604–611 in V2, require 612–667 to remain zero, and keep the existing 672-byte size, bitset offsets and CRC at 668. New V2 saves set the met-location-format status bit at creation. Keep V1 validation frozen; both ROMs and the launcher must agree on the V2 descriptor. Independent format review found no current use of bytes 604–611; this layout also keeps the first-six-chunk link-save margin at 20 bytes.
- Translate donor identifiers into the shared engine at import time. The original host and donor have different save-sector layouts and item-number collisions; the two released ROMs must instead share a verified player-data contract. Transfer only the common player fields between their regional saves; never import source-engine raw saves or silently discard unsupported data.
- Keep the existing 80-byte boxed Pokémon and 100-byte party Pokémon layouts. Cormoria map sections need logical IDs 250–300, while the met-location byte uses 250–255 for "none", unused locations and special met locations. A marker in the six unused `PokemonSubstruct0` bits distinguishes Cormoria locations in a save explicitly identified as V2. Raw Pokémon bytes alone cannot establish that format because a checksum-valid V1 Pokémon could already carry the marker. New V2 saves initialize the marker format at creation and reject V1 Pokémon transfers. Reserve distinct logical values for old none (301), unused bytes 251–252 (`0x3FFB`–`0x3FFC`) and specials 253–255 (`0x3FFD`–`0x3FFF`). Verify every Pokémon read/write, display, and link path before activating Cormoria maps. This replaces the direct 14-bit packing proposed in the superseded combined-ROM plan.
- Common menus and gameplay definitions must be reconciled explicitly. Persist regional quest/key-item effects with their owning campaign. Shared inventory must retain the origin and meaning of every item.
- Stop the old emulator before activating the destination. Commit arrival only after destination import, save and bridge verification succeed. Failed or interrupted transitions retain the departure save and a recoverable transaction.
- Preserve co-op character/group identity while replacing the ROM-specific bridge and presence location. Server compatibility must distinguish a compatible release family from exact ROM identity.

## Contract for additional ROM worlds

Cormoria is the first added world, not a special case in the travel protocol. A world registry owns immutable `world_id` values; each entry names its build profile, ROM artifact, matching bridge manifest, regional save namespace, supported shared-player schema, entry/exit portals and allowed destinations. Portal scripts send a stable portal ID; the trusted release catalog derives its destination world and arrival ID. On a first visit, that arrival selects a release-pinned save template produced and saved by the destination ROM at the intended map and tile. On later visits, the destination's last committed world-local save preserves its return position. Continue loads the saved map, layout, coordinates, map view and object templates, so changing only a warp/map ID is unsafe. Keep world IDs stable across releases and reject an unknown, retired or incompatible world before checkpointing.

Keep the content importers region-specific but the build and travel mechanisms world-agnostic. Each importer authenticates its donor and appends a complete, ordered block of map groups, layouts and section IDs to the registry; it must verify the registry prefix it builds upon. Cormoria's current authenticated generator is anchored to the pre-Cormoria registry, so the next region must allocate after the Cormoria tail rather than reuse that generator's 79-group/1,192-layout baseline. The common validator should check the final catalog for duplicate IDs, filenames, save namespaces and overlapping location ranges before building any ROM profile. Run the map/layout generator with a synthetic third world whenever that common validator changes.

Item IDs are shared-player identities, unlike each ROM's local event flags. Allocate new items once in the append-only shared item registry and include the same ItemInfo semantics in every ROM that can receive the player. Cormoria's 30 distinct new items reserve IDs 890–919; later regions append after 919 or reuse an existing global item with proven matching meaning. Never carry the donor's numeric item IDs into a shared save, because they collide with host items.

The first shared item table now installs those 30 definitions in both ROM builds. Splash is HM10 at global ID 902, and the common machine list resolves its move; three donor Drive pictures use the host's shared Drive picture with their original palettes. The item, key-item and TM/HM bag capacities are 40, 64 and 90 slots. This changes the shared SaveBlock1 layout and sector-five checksum length in both ROMs and the co-op save reader. Fresh saves are acceptable, but every region in the same release must use the identical layout so travel retains the complete bag. Future item-registry additions must include the same definition and bag-capacity check in every receiving ROM before travel is enabled.

Keep `world_id`, engine region ID, map group/number and logical map-section ID as distinct identities. A ROM can contain more than one engine region, while a later ROM may contain a single new region. Never infer the destination artifact from a section number or assume the only other world is Cormoria. The registry is the source of truth for which portal connects which worlds and which section allocation belongs to each world. A release validator must check unique IDs and namespaces, portal targets and reciprocal return routes, reachability of every world from the default world, compatible shared schemas, and artifact/bridge pairs before any ROM can offer travel.

The shared player snapshot has one versioned schema and explicit ownership rules. It includes trainer identity, options, menu settings, party and all stored Pokémon, Day Care/fusion storage, mail and held items, inventory and currencies, Pokédex and co-op identity. A world save owns its own map position, story flags, quest journal, badges, trainers, puzzles and region-only service state. Item and Pokémon identities are common across builds; a missing definition in the destination is a transfer error, never a reason to drop an object. Regional key items may remain in shared inventory only when their identity and ownership are preserved and they cannot trigger another world's story.

Derive shared-field offsets and lengths from the compiled ROM save structures and publish them in each ROM's verified bridge descriptor. The launcher must compare those descriptors before transferring a player; hand-maintained offsets or a raw SaveBlock1/SaveBlock2 copy would silently mix shared data with map and quest state. Keep each destination save's encryption key and re-encrypt copied money, coins, bag quantities and any shared game-stat or berry-powder values under that key. Copying the source key would corrupt encrypted values retained from the destination campaign. The selected Flash1M slot's physical-sector rotation, per-sector checksums, SaveBlock3 co-op record and optional RTC trailer must survive staging and reparsing. A synthetic third ROM with a different regional save image should exercise the same field projection and transaction code before portals become active.

Before activating travel, classify every persisted field as shared player state, world-local state, a world-local asset held in safe custody (such as a Pokémon left at a regional Day Care), or an explicitly transformed value. The inventory must cover SaveBlock1, SaveBlock2, Pokémon storage, SaveBlock3 and appended regional records. Player origin, rival name, play time, clock offsets, game statistics, Day Care, registered item and decorations need explicit decisions; unclassified bytes are a failed transfer contract, not disposable padding. A later ROM supplies its own regional field schema but consumes the same shared-player descriptor and projector. Tests must show that an intervening trip through another ROM leaves a third world's untouched state byte-identical.

Travel is a journaled transaction keyed by source world, destination world, player identity and monotonically increasing checkpoint ID. Checkpoint the source, validate and stage the complete shared snapshot into the destination's save, verify it without activating it, stop the source, launch the catalog-selected destination ROM, and acknowledge arrival before committing the active-world pointer. A retry uses the same checkpoint and must not duplicate inventory or Pokémon. On any failure, the source remains recoverable; a later trip back reads its own world progress and the latest authoritative shared player state. Co-op disconnects the old bridge session and reconnects under the same character/group identity with the destination's verified manifest. These steps take world IDs; they do not assume exactly two worlds.

The launcher must hold a durable per-character journal outside its temporary session workspace, with one active-world pointer, trusted release-catalog digest, cloud revision/fence, authoritative shared-state digest and generation, and a per-world last-imported full-save hash and generation. Before projecting into a destination world, verify that its save exactly matches the inactive image recorded in the journal; generation alone is insufficient because it can wrap or be copied. The active source's validated co-op record is authoritative for shared identity and progress; copy and reseal that record along with shared player fields, while retaining the destination's regional campaign record. A divergent destination fails closed until an explicit conflict or merge policy is defined. Comparing entire co-op records for equality cannot implement return travel: ordinary saves change the generation and regional progress. The generic transfer path must handle the co-op record in SaveBlock3's 15 logical 116-byte chunks as well as selected-slot player sectors. Recompute the V2 CRC, reparse the complete staged image, and commit the active-world pointer only after destination arrival is acknowledged. Keep the set of world IDs and portal edges in the catalog, not in this algorithm; a third ROM exercises the same authority check, projection and crash recovery. CoopSave V2's five regional-progress slots are a bounded format, so a sixth engine region needs a reviewed schema revision before its catalog entry is admitted.

Map locations need a separate, stable global identity. The host has 250 section IDs before Cormoria, whose planned IDs are 250–300. The map-header type and generator now carry 16-bit IDs; several UI/save consumers still hold a single byte, so importing Cormoria maps before auditing them would still silently truncate IDs above 255. Widen the active map-UI section path before runtime registration, and audit every persistent 8-bit consumer: widen it, translate through an explicit world-qualified adapter, or reject an unsupported value. Keep the published world/section-to-logical-location allocation in the registry, and reject collisions and values outside the Pokémon met-location codec's capacity at generation time. V2's current codec recognizes Cormoria only through 300; extending that range for another world requires a reviewed codec/schema change and round-trip coverage. No future world may reuse Cormoria IDs merely because it lives in another ROM.

Adding a world should then require its content/build profile, registry entry, section allocation, regional save schema and portal definitions, plus compatibility tests against every allowed travel edge. It must not require a new copy of the transaction engine, shared-player serializer or launcher flow. The current V2 regional record layout is sized for Cormoria; a later world's progress needs an explicit schema revision rather than borrowing unused bytes by convention.

The first release must exercise the same registry and transaction path with two entries; adding a third should be a data-and-content change unless that world needs a deliberate shared-schema or location-codec revision. Preserve every registered world's regional save when traveling between other worlds, but reject unknown shared-player fields or objects rather than silently dropping them. Test each permitted directed edge, including return trips and interrupted switches, instead of testing only the Hoenn-to-Cormoria path.

### Runtime boundaries for more than two ROMs

The existing `data/rom_worlds.json` selects build content. It is not sufficient to authorize travel: it has no verified ROM hash, save namespace, portal, or bridge identity. The release catalog must reference its stable `world_id` and supply those runtime fields for each world. Validate the two catalogs together when packaging a release, so a build entry cannot silently drift from the ROM that the launcher starts. A portal supplies only its stable portal ID; the pinned catalog derives the destination artifact, arrival ID, and a destination-ROM-written save image for a first visit. The release validator invokes the same V2 save parser as the server, checking the template's digest and saved map; the server rechecks and caches it at startup. No portal script or save file may supply an executable path.

Persist the active world separately from an indexed collection of regional saves: `regional_saves[world_id]`. Keep one authoritative, versioned shared-player snapshot. A successful arrival updates that snapshot and the active-world pointer atomically with the travel checkpoint; saves for worlds not involved in the trip are left intact. This same representation must handle main → Cormoria → a third world → main without a pair of `main_save`/`cormoria_save` fields or special return logic. A destination never becomes active solely because its emulator launched; it must acknowledge import of the expected checkpoint.

Keep three compatibility checks distinct. The shared-player schema decides whether every Pokémon, item, setting, and co-op identity can cross. The regional save schema decides whether the destination can resume its own story state. The world-location codec decides whether origin and arrival locations can be represented without truncation. The current fixed five-record V2 save and Cormoria-limited Pokémon location codec are version-two choices, not implied capacity for future worlds. A later region that exceeds either format must introduce and validate a new schema before its catalog entry becomes travel-enabled. Adding a region must never silently reinterpret V2's reserved bytes or recycle a retired world ID.

The reusable transfer engine should accept catalog entries and a checkpoint record, then validate source and destination, stage the shared snapshot, verify the destination save, request the switch, and acknowledge or recover. World-specific code is limited to content, regional state, arrival portals, and explicit adapters for new shared objects. Test the engine against a synthetic third catalog entry before coupling it to Cormoria's real campaign.

Treat the registry as an append-only identity ledger. Allocate each new world's ID, build bit, save namespace and logical location interval once; keep retired IDs reserved. A release catalog entry also declares its shared-player schema range, regional-save schema, location-codec version, object-catalog fingerprint, ROM digest, bridge-manifest digest, player-transfer-manifest digest and portal table. Validate all entries and every allowed directed portal edge before packaging. Extract the player-transfer descriptor from each linked ROM, compare it with its manifest and require the same complete descriptor digest across all travel-compatible worlds. The launcher opens only artifacts selected by this validated catalog; save data and ROM scripts carry IDs, never filesystem paths. Keep map group/number and engine-region IDs local to content, since neither is a stable cross-ROM identity.

Separate the two save layers explicitly. The launcher indexes complete regional save images by `world_id`, and only the currently active world's image is mounted. Inside that image, campaign-owned flags, trainers, variables, quests and return position use that world's regional record and checked accessors. The shared player snapshot is a single versioned authority, not a copy of whichever ROM was last played. Adding a third ROM therefore adds a regional image and record adapter without adding a third branch to the transfer algorithm. The fixed five-record CoopSave V2 and the Cormoria location encoding remain explicit limits; expanding either requires a new compatible schema and a migration or a fresh-save policy, never reuse of reserved bytes.

Use one transaction state machine for every edge: `idle → source_checkpointed → destination_staged → destination_verified → launched → arrival_acknowledged → committed`. Persist the checkpoint ID, source/destination world IDs, source snapshot digest, destination staged-save digest and previous active-world pointer before launch. Replaying any step with the same checkpoint is idempotent. If validation, launch or arrival fails, recover the source image and pointer; never promote a destination merely because its process started. A return trip loads that world's existing regional image and overlays the newest authoritative shared snapshot, leaving all unrelated regional images byte-for-byte unchanged.

The compatibility gate must account for every shared object, not just the schema number: all occupied party/PC/Day Care/fusion Pokémon, held items, mail, bag and PC items, currencies, Pokédex, options, menu state and co-op identity must encode and decode identically in both ROMs. Check object-catalog fingerprints before checkpointing, and verify a staged save by decoding and comparing the full shared snapshot before launch. A world missing any active object is ineligible for travel. Bridge admission keeps the same player/group identity but selects the destination's manifest and presence location by `world_id`.

Berry plots belong to the per-world save image. The shared engine now reserves 192 berry slots: Hoenn's existing range, Johto 90–124, Cormoria 125–153, and capacity for later allocations. The Cormoria importer translates all 29 donor IDs, including unused reserved names, and its new-game seed matches the donor's 24 planted plots. A later ROM can use unused slots within its own image only after declaring a checked allocation; if a world needs more than 192, it must revise the shared save layout and transfer descriptor for every ROM in that release. The launcher must retain each world's full regional image so berry growth and harvest resume when the player returns.

The first reusable-flow test should register three lightweight fixture worlds and exercise all permitted directed edges, including `main → cormoria → third → main`, reverse travel, a repeated checkpoint and failures before and after launch. It must assert exact shared-state equality, independent regional progress in all three images, no item or Pokémon duplication, and a single co-op identity. Run the same contract against the two real ROMs and emulator saves before enabling portals. This fixture proves the number of worlds is not wired into the engine; it does not substitute for a playable Cormoria campaign.

The build selector now reads `data/rom_worlds.json` for names, immutable world IDs, unique membership bits and ROM build metadata. `mapjson` accepts a world name, an explicit list of owning worlds, or `shared`, which expands to every registered build bit; legacy maps/layouts remain in the default world. The Makefile resolves a registered name or bit before passing the bit to C and assembly, and registry edits regenerate map/layout tables. Tests cover a synthetic third world and reject duplicate bits, IDs, artifact names and game codes. A separate release-catalog validator now verifies a caller-pinned catalog digest, all registered worlds, ROM and bridge hashes, bridge/ROM save-schema pairing, shared object identity, disjoint owned location-section ranges, save namespaces and reciprocal portals in a synthetic three-world fixture. The actual signed catalog, cross-release identity ledger and travel runtime are not implemented yet.

The build selector now also passes `ROM_WORLD_ID` alongside `ROM_WORLD`. The latter remains a power-of-two content membership bit; the former is the persistent catalog identity. A synthetic third world uses membership bit 4 and world ID 7 to prevent accidental dependence on their matching values in the first two profiles. The Rust co-op protocol exposes a separate nonzero `RomWorldId` type; it does not reuse `RegionId`, which identifies a gameplay/co-op region rather than a ROM artifact.

`data/rom_world_ids.lock.json` now reserves assigned and retired world IDs across build-registry edits. Active worlds must appear in the lock with their original ID; removing a world leaves its ID reserved. A new ROM region appends a new name/ID pair before its build profile is accepted. The lock is a source-control contract, not a substitute for signing and verifying the release catalog at runtime.

Before enabling travel, exercise the release catalog and transfer engine with a synthetic third ROM: switch main → Cormoria → third → main, verify the same shared player state and co-op identity at each arrival, and verify that all three regional saves retain their independent progress and return locations. The test must use catalog entries and portal IDs, not a Cormoria-specific branch. A new world may supply its own content adapter, but must not require changes to the shared transfer algorithm; reject worlds whose save schema, location allocation, object catalog or artifact identity cannot be represented by the release family.

## Shared player transfer contract

| State | Travel rule |
| --- | --- |
| Player identity and settings | Carry trainer identity, appearance, options and common menu state to the destination. |
| Pokémon | Carry the party, every PC box, fusion storage and Day Care Pokémon with held items, mail and exact V2 met locations. Validate every occupied Pokémon before committing arrival. |
| Inventory and economy | Carry all shared bag pockets, PC items, registered item, money and coins through stable item identities. Region-only quest items retain their owning region's semantics. |
| Pokédex and co-op | Carry shared collection progress and the co-op character/group identity. Establish a fresh ROM-specific bridge and presence session after launch. |
| Regional world | Keep each world's position, quests, flags, badges, puzzles, NPC changes, TV shows/interviews and services in that world's save. A return resumes that world without replacing its progress with another world's bytes. |

The transfer schema describes fields and stable identities, not raw source-ROM save offsets. The signed release catalog must enumerate each world's ROM and matching manifest as a fixed artifact pair; a portal cannot provide a filesystem path or hash of its own. Validate the source and destination world catalog entries, release family, transfer schema and artifact hashes before copying. Stage destination writes, verify the result, and commit the world switch only after arrival succeeds. A later ROM region uses the same transaction and supplies its own catalog entry and regional-state schema.

## Completion evidence

Both ROMs build from pinned inputs. A real round trip retains shared player data and independent campaign progress. Co-op reconnects to the correct world without duplicating a live player. Failure recovery loses neither Pokémon nor items. Changes have independent code review and focused regression coverage. Merely generating a manifest, writing a converter, or passing mocked orchestration tests does not establish completion.

## New V2 save checkpoint

The read-only `coop-save` view exposes payloads from the validated, selected logical sectors without rewriting the Flash1M image. Its 24 focused tests pass. An earlier wide met-location prototype failed independent review because checksum-valid legacy Pokémon can already carry the proposed escape marker, and it lost the old unused values 251 and 252. The corrected, independently reviewed V2-only codec is on this branch. It preserves those values, while the live getter and setter remain unchanged. Its focused Linux ROM test passed 27 tests, with one pre-existing `KNOWN_FAILING`. Travel must admit Pokémon only from a validated V2 player authority.

The reviewed schema-two definition exists in the C header without changing the live V1 loader or writer. Pure C V2 validation and CRC helpers agree with the matching Rust `coop-save::v2` parser on the five ordered regional records, registry, CRC, status bits, badge and identity ordinals, and zero tail. The Rust V2 API also validates the ROM-selected Flash1M slot, retaining exact image and RTC bytes without falling back to an older slot. All 33 focused `coop-save` tests pass. A Linux `make -j6 check TESTS=Cloud` ROM run passed 127 tests, including the three new V2 tests, with eight pre-existing `TO_DO` results. These are inactive validation paths. The copied-save migration helper and V1 upgrade step were removed after legacy-save compatibility left scope. New V2 save creation, validated bidirectional player transfer, live V2 writing, and ROM switching remain prerequisites before travel can be enabled.

Read-only discovery of the live save path found that V2 cannot be activated by changing `src/coop/save.c` alone. New-game initialization, loading, canonical-save rollback, and bridge admission currently call V1 APIs; the manifest generator, Lua bridge, launcher compatibility check, and cloud save validator also require schema one. The normal Pokémon met-location getter/setter and egg/trade producers still write the old byte format. The activation unit must cover these boundaries together: create fresh V2 with the met-location-format bit, retain all five regional records through save/reload, make the ROM and external validators agree on V2, and reject V1 as a traveling player authority. It must verify a ROM-created Flash1M image through Rust's selected-slot V2 parser. Frozen V1 validation can remain available without a migration path.

Pure V2 initialization and sealing now construct the five ordered progress records, registry binding and CRC without touching live V1 state. An independent data-integrity review confirmed the ABI but identified a mandatory activation gate: the initializer sets the met-location-normalized flag, while active Pokémon getter/setter and egg/daycare/trade producers still use raw bytes. Do not call the V2 initializer from new-game creation until every Pokémon creation and transfer path uses the V2 codec, or set the flag only after an explicit scan that proves all occupied Pokémon normalized. A passing pure V2 test does not prove this live invariant.

The authenticated content importer now stages all 165 Cormoria maps and layouts, 188 namespaced script sources and the pinned asset inputs outside the live registries. Live registration depends on adding six map groups, 165 layout entries, 51 section records, 59 tileset definitions and converted assets, and script includes; the 122 donor native bindings and three external map edges still need host adapters. Keep each donor map's group and number stable. A one-map registration at a later group/index would require temporary null slots throughout `mapjson`, so test an isolated map-header/layout fixture first, then register the full ordered campaign and measure linked ROM size. Do not treat a successful stage as a playable world.

The next content unit is an authenticated, full-order maps/layouts registration generator against the staged v5 manifest. Append Cormoria groups 79–84 with map counts 28/32/40/31/30/4, install all 165 map JSON files and layout records in that order, rewrite layout binary paths to namespaced installed files, and verify `mapjson` output for both world profiles. Keep this generator probe separate from live campaign activation until tileset conversion, script/native closure, map art and region/co-op routing are ready. A generator fixture alone does not prove the campaign fits the remaining ~4.3 MiB of Cormoria ROM space; measure the complete asset link.

The section registration generator now authenticates its staged donor input and produces the 51 append-only records as a preview, correcting two stale donor display names. The popup-theme tables have a safe bound for those future IDs. The live section table remains unchanged until the remaining single-byte consumers and location codec are ready for `MAPSEC_NONE` to move from 250 to 301.

An isolated full-order map/layout registration probe now generates both ROM profiles and all 165 Cormoria map headers. A full Cormoria link probe stops in map-event assembly because donor event constants and Cormoria-owned flag IDs are not installed. Hidden-item events need special care: the host macro packs a flag offset from `FLAG_HIDDEN_ITEMS_START` into a 32-bit event argument, while the Cormoria allocation starts at `0x8000`. Merely defining those symbols would overflow the packed field. Resolve this through a reviewed world-owned event/flag adapter and matching save storage, preserving the campaign's 483 flags, rather than aliasing them to host flags. The same world-qualified storage pattern should support later ROM regions.

The event-storage discovery resolved where those regional bits belong: append a versioned, CRC-checked `WorldEventSaveV1` record after Johto's record in SaveBlock1 sector 5, without changing the shared CoopSave V2 ABI. The five SaveBlock1 sectors provide 19,840 data bytes; the current 16,416-byte shared SaveBlock1 prefix and 372-byte Johto record leave 3,052 bytes for the generic record. The 1,548-byte record leaves 1,504 sector-five bytes free. Its 4,096-bit flag set, 4,096-bit trainer set and 256 `u16` variables use 1,536 data bytes plus header and CRC. Each ROM's save image holds its own copy, so a later ROM can use the same record and accessor interface without appending all prior regions' state to every image. A world exceeding those capacities needs a reviewed regional schema revision. Runtime dispatch must intercept Cormoria's `0x8000` flags and `0x9100` vars before legacy pointer arithmetic. Hidden-item events must encode a local ordinal and resolve it through the same world-qualified adapter in pickup and Itemfinder paths.

Dreamstone's quest journal has 20 five-state quests and 21 subquest-completion bits. It cannot be copied from the donor's SaveBlock2 because that block also owns common player identity and options. Reserve a manifest-checked, world-local 121-bit window inside `WorldEventSaveV1` flags for this campaign, and expose it through Cormoria quest state accessors. Other ROMs can use their own noncolliding local allocation within their own regional record or introduce a new schema when capacity is insufficient; no travel code interprets quest bits. The quest UI and script commands must still be ported with real behavior, including opcode remapping away from host `0xE5`/`0xE6`.

## Section-width checkpoint

The map-header generator and C `MapHeader` now carry 16-bit section IDs, with 32-byte aligned headers; a two-header assembly fixture checks section 256 and the following label offset. The overworld section getters and map-preview path now also carry 16-bit IDs, including the preview task's stored section. The exact combined patch passed the Linux ARM `make -s -j6 check TESTS=Cloud` run: 127 passed and eight pre-existing `TO_DO`. Region-map island and old Aqua Hideout predicates now accept full-width section IDs so a later section cannot alias a low-byte special location. The six region-map grids, landmark lookup and runtime Match Call path also preserve the 301 sentinel in an isolated expanded-section build. Six TV show records and Gabby and Ty now retain full sections without enlarging their saved records.
